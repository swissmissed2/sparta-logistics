## 2026.05.25

### 파티션 키 전략: `orderId` / `deliveryId` 분리

**배경**

Kafka는 같은 파티션 내에서 프로듀서가 보낸 순서를 보장한다.
파티션이 여러 개인 환경에서 순서가 중요한 이벤트가 있다면, 비즈니스 식별자를 파티션 키로 지정해야 한다.
같은 키를 가진 메시지는 항상 같은 파티션으로 라우팅되므로, `orderId`를 파티션 키로 쓰면
동일 주문의 이벤트가 컨슈머 측에서 순서대로 처리된다.

배달의민족에서 `배차완료 → 픽업완료 → 배달완료` 순서 보장에 파티션 키를 활용한 사례를 확인했고,
이 프로젝트의 주문 Saga 이벤트와 배송 생명주기 이벤트에도 동일하게 적용하기로 결정했다.

**결정**

| 이벤트 그룹 | 파티션 키 | 이유 |
|---|---|---|
| 주문 Saga 이벤트 (`order.created`, `stock.reserved`, `stock.reservation.failed`, `cancel.delivery.command`, `restore.stock.command`, `delivery.cancelled.ack`, `stock.restored.ack`, `delivery.started`) | `orderId` | 동일 주문 이벤트가 같은 파티션으로 수렴되어 Saga 체인 순서 보장 |
| 배송 생명주기 이벤트 (`delivery.created`, `delivery.creation.failed`, `ai.deadline.calculated`) | `deliveryId` | 배송 단위 순서를 주문 Saga와 독립적으로 보장 |

### 주문 ACCEPTED 전이 시점: `totalDeliveryCount` 방식 (Option B1) 채택

**배경**

초기 `StockReservedEvent` 설계에서는 `sourceHubId`가 이벤트 최상위에 단일 값으로 존재했다.
즉 "하나의 주문 = 하나의 출발 허브 = 하나의 배송"을 전제하고 있었다.

그런데 `OrderItemPayload`를 보면 아이템마다 `hubId`가 개별로 붙어 있어,
하나의 주문에 서로 다른 허브의 상품이 섞일 수 있는 구조였다.
이 불일치를 해소하기 위해 `sourceHubId`를 아이템 레벨(`StockReservedItemPayload`)로 내렸고,
그 결과 DeliveryService는 출발 허브별로 배송을 1건씩 생성하게 됐다.

이 변경으로 하나의 `orderId`에 대해 `delivery.created`가 N번 발행될 수 있는 구조가 됐다.
여기서 "몇 번째 이벤트를 받았을 때 주문을 `ACCEPTED`로 전이할 것인가"라는 새로운 질문이 생겼다.

**선택지 비교**

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 첫 번째 `delivery.created` 수신 즉시 ACCEPTED | 구현 단순 | 나머지 배송 생성이 실패해도 ACCEPTED 유지 (비즈니스 의미 불일치) |
| **B1** | `DeliveryCreatedEvent`에 `totalDeliveryCount` 필드 추가, 수신 수가 해당 값에 도달하면 ACCEPTED | 기존 흐름 변경 최소화, 정확성 보장 | OrderService에 주문-배송 매핑 테이블(`p_order_delivery`) 필요 |
| B2 | DeliveryService가 N건 생성 완료 후 단일 집계 이벤트를 별도 발행 | OrderService 로직 단순 | 새 토픽 추가, DeliveryService에 완료 판단 로직 필요 |

**결정: B1 채택**

B2는 토픽 추가와 집계 로직이 생겨 현재 규모에서는 오버엔지니어링이라고 판단했다.
`totalDeliveryCount` 필드 하나로 정확성과 변경 최소화를 동시에 만족하는 B1을 채택했다.

### Kafka 발행 정합성: 단기 retry + 멱등성, 장기 Outbox 패턴 공통 도입

**배경**

DeliveryService가 `stock.reserved`를 수신하면 출발 허브별로 배송을 N건 생성하고
`delivery.created`를 N번 발행한다. 여기서 두 가지 정합성 문제가 제기됐다.

1. **N건 생성 도중 크래시**: 일부 배송만 DB에 저장되는 partial state 발생 가능
2. **DB 저장 후 Kafka 발행 실패**: DB에는 배송이 존재하지만 다운스트림 서비스가 이벤트를 영영 받지 못함

문제 2를 완전히 해결하려면 `p_outbox` 테이블을 도입해야 한다.
하지만 OrderService나 HubService에서도 동일한 리스크가 존재하기 때문에,
DeliveryService만 먼저 Outbox 패턴을 적용하는 것은 일관성 면에서 비효율적이라고 판단했다.

**결정**

| 단계 | 전략 |
|---|---|
| **1차 (기능 구현)** | N건을 단일 `@Transactional`로 묶어 문제 1 제거 + Kafka 실패 시 retry + 컨슈머에서 처리된 `event_id`를 DB에 저장해 중복 처리 방지 |
| **2차 (안정화 후)** | `p_outbox` 테이블 + `@Scheduled` 폴러를 공통 모듈로 팀 전체가 함께 적용 |

배달의민족에서는 Debezium이 binlog를 읽어 Outbox 테이블 변경을 Kafka로 내보내는 CDC 방식을 사용했지만,
이 프로젝트에 CDC 인프라까지 구성하는 것은 오버스펙이라고 판단했다.

**`event_id` 생성 방식**

이벤트를 발행하는 서비스가 Kafka에 발행하는 시점에 `UUID.randomUUID()`로 새로 생성한다.
주문 생성 시점의 ID와는 별개이며, 이벤트 단위의 식별자로 사용된다.

### 재고 차감 시점: 예약(`order.created`)과 실제 차감(`delivery.started`) 분리

**배경**

Step 1-2에서 HubService가 `order.created`를 수신하면
재고를 예약(`available - N`, `reserved + N`)한다는 점은 명확했다.

하지만 `reserved`를 언제 차감할지, 즉 재고를 실제로 소비하는 시점이 SA 문서 상에서 명시되어 있지 않았다.

`HubStock` 엔티티에는 `available`과 `reserved`가 분리되어 있고,
`HubStockLog`에는 `orderItemId`(예약 시점 추적용)와 `deliveryId`(출발 시점 추적용) 필드가 함께 존재한다.
DB 스키마 자체가 두 시점을 구분해 기록하도록 설계되어 있었다.
또한 `HubStockChangeType`에는 `ORDER_DECREASE` 같은 주문 시점 타입은 있지만
배송 출발 시점에 해당하는 타입이 없어, 구현 전에 명시적으로 결정해야 하는 상태였다.

**취소 시 보상**

| 취소 시점 | 복구 방식 |
|---|---|
| `delivery.started` 수신 전 (`reserved` 보유 중) | `reserved - N`, `available + N` |
| `delivery.started` 수신 후 (실제 차감 완료) | `available + N`만 복구 |

두 경우 모두 `restore.stock.command`를 소비한 HubService가 현재 재고 상태를 확인해 처리한다.
